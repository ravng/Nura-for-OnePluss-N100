QRTR/RMTFS BREAKTHROUGH
=======================
The current Alpine qrtr package no longer ships legacy qrtr-ns. This downstream 4.19 kernel REQUIRES userspace qrtr-ns. Without it, qcom_smd_qrtr logs:
  failed to create endpoint

Legacy qrtr-ns was built from linux-msm/qrtr tag v1.2. Starting it before the modem makes QRTR work:
  /usr/local/sbin/qrtr-ns -f

The current upstream rmtfs expects /sys/class/remoteproc and fails with:
  Failed to get rprocfd

A patched rmtfs was built. Its rproc fallback opens /dev/subsys_modem, holds that descriptor, and treats start as a no-op. It is installed on the live root as:
  /usr/local/sbin/rmtfs-downstream

rmtfs also needs the downstream UIO alias. The installed udev rule creates it after retriggering:
  udevadm trigger /sys/class/uio/uio0
  udevadm settle
  /dev/qcom_rmtfs_uio1 -> uio0

Then this succeeds and remains running:
  /usr/local/sbin/rmtfs-downstream -s -P -r

With qrtr-ns started first, the modem boots stably and qrtr-lookup lists many services. Confirmed kernel log:
  Modem has booted up

The current upstream pd-mapper also assumes /sys/class/remoteproc and exits:
  pd-mapper: failed to open remoteproc class
  no pd maps available

A legacy pd-mapper from linux-msm/pd-mapper commit 9543190 was built. It accepts explicit JSON map arguments and is installed as:
  /usr/local/sbin/pd-mapper

Start it BEFORE rmtfs/modem with:
  /usr/local/sbin/pd-mapper \
    /vendor/firmware_mnt/image/adspr.jsn \
    /vendor/firmware_mnt/image/adsps.jsn \
    /vendor/firmware_mnt/image/adspua.jsn \
    /vendor/firmware_mnt/image/cdspr.jsn \
    /vendor/firmware_mnt/image/modemr.jsn \
    /vendor/firmware_mnt/image/modemuw.jsn

modemuw.jsn maps provider/service wlan/fw to msm/modem/wlan_pd, QMI instance 180.

With this ordering the kernel reached a new state:
  service-notifier: Connection established between QMI handle and 180 service

This proves QRTR, rmtfs, PD mapping, and the modem root protection domain are substantially correct. However, QMI service 69 still did not appear and ICNSS never reported WLAN FW ready.

Two changes were required:
1. Preserve the complete custom firmware path read from `/sys/module/firmware_class/parameters/path`; trim only an actual newline.
2. Before scanning `/sys/class/remoteproc`, directly try `<custom-firmware-path>/<requested-relative-file>`.

Built live binary:
  /tmp/tqftpserv-downstream

With the custom firmware tree at `/run/billie2-firmware`, patched tqftpserv served:
  /readonly/vendor/firmware_mnt/image/wlanmdsp.mbn
  size 3892648 bytes
  507 acknowledged TFTP blocks

After transfer:
  qrtr-lookup showed service 69, version 1, instance 0: ATH10k WLAN firmware service
  service-notifier reported msm/modem/wlan_pd up
  ICNSS logged `QMI Server Connected: state: 0x580`

However, no `WLAN FW is ready`/FW_READY indication appeared and writing ON to `/dev/wlan` still timed out. The next investigation must start from ICNSS QMI state 0x580: inspect the indication registration/MSA handshake and determine which state bit or firmware response is missing after successful wlanmdsp transfer.

Further state decoding:
- ICNSS state enum bits: bit 0 WLFW_CONNECTED, bit 1 POWER_ON, bit 2 FW_READY, bit 7 SSR_REGISTERED, bit 8 PDR_REGISTERED, bit 9 PD_RESTART, bit 10 WLFW_EXISTS, bit 13 FW_DOWN.
- Before a manual modem restart, ICNSS reported state `0x2583`, which includes WLFW_CONNECTED, POWER_ON, PD_RESTART/WLFW_EXISTS-related state, and critically FW_DOWN, but not FW_READY.
- On reconnect it logged `QMI Server Connected: state: 0x782`, then `Invalid Hang Data details, Offset:0x0, Length:0x0`.
- This points to the WLAN firmware entering a failure/rejuvenation path after transfer/QMI publication, rather than a remaining transport or missing-file problem.

2026-10-29 LATEST EXPERIMENTS
=============================
The rejuvenation hypothesis was tested without flashing. A tiny module changed the
global ICNSS `quirks` value at runtime. `/proc/kallsyms` exposed the initialized
global symbol as:
  ffffff8009f64dc0 D quirks
The address is stable on the tested boots, but future work must discover it from
`/proc/kallsyms`, not hard-code it.

Setting quirks from `0x80` (FW_REJUVENATE_ENABLE) to `0` removed FW_DOWN and
rejuvenation state but did not produce FW_READY. Detailed IPC logs proved that
the transport and most of the ICNSS handshake are working:
  - WLFW server arrives at QRTR node 0 port 83.
  - indication registration succeeds.
  - MSA memory info sends two regions at 0x51900000 totaling 0x100000.
  - MSA ready request succeeds and MSA Ready Indication arrives.
  - capability query succeeds.
  - chip_id 0x120, family 0x4007, board_id 0xff, soc_id 0x40670000.
  - firmware WLAN.HL.3.2.4.c2.1-00007-QCAHLSWMTP, timestamp 2020-10-22.
  - firmware still never sends QMI_WLFW_FW_READY_IND.
`Invalid Hang Data details, Offset:0x0, Length:0x0` accompanies MSA ready but is
not evidence of a firmware crash by itself. The earlier conclusion that the
firmware immediately entered rejuvenation/FW_DOWN was disproved.

UBUNTU TOUCH IPA DISCOVERY
==========================
The upstream Ubuntu Touch billie2 port contains:
  overlay/system/etc/init/ipa_fws.conf
Source:
  https://gitlab.com/ubports/porting/community-ports/android10/oneplus-nord-n100/oneplus-billie2
It waits for `/vendor`, checks `/vendor/firmware/ipa_fws.mdt`, and writes `1` to
`/dev/ipa`. This was missing from the native Alpine startup.

On Nura, the native sequence must first point firmware_class at vendor firmware:
  printf %s /vendor/firmware > /sys/module/firmware_class/parameters/path
  printf '1\n' > /dev/ipa
Without setting the firmware path first, the write blocks in the kernel fallback
loader. With the correct path, dmesg proves:
  ipa_fws: loading from 0x56100000 to 0x56105000
  ipa_fws: Brought out of reset
and `rmnet_ipa0` appears.

After IPA firmware is loaded, a forced stock qcacld probe reports:
  SMMU S1 enabled
This conclusively fixes the earlier IPA:disabled/WLAN:enabled mismatch without a
locally patched WLAN module. Keep the stock OxygenOS module.

However, forcing SKIP_QMI is still invalid. Even with IPA firmware and the stock
matching qcacld module, the firmware rejects the premature config request:
  QMI Config request rejected, result:1 error:90
  Failed to complete BMI phase, status:16
Therefore the sole remaining blocker before wlan0 is genuine
QMI_WLFW_FW_READY_IND. IPA initialization is a required fix, but not sufficient.
